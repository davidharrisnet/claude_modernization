MasterAntiqueRepair · database migration · import-oracle (proof of concept)

Connecting to the MasterAntiqueRepair Oracle database

The migrated database runs in an Oracle AI Database 26ai Free container on the Linux machine. This guide takes you from a first query in SQL*Plus to a Spring Boot 4.1.1 application that reads it with JDBC and JPA, including the password change every migrated user is forced to make on first login. Every command and file here was run against a copy of this database before it was written down. Phase 2 uses the PostgreSQL database; this is the same path shown for Oracle.

The tables hold 12 users (1 manager, 3 employees, 8 customers), 24 repair tickets (8 each SUBMITTED, INPROGRESS, COMPLETED), 26 comments, 78 audit log rows and 12 user-role links. Names are lowercase snake_case in the SQL (created_at, user_id) and unquoted, so Oracle stores them in upper case and you can write them in any case without quotes; never write them in double quotes in lower case ("users" does not exist).

Three things are locked down on purpose. The container publishes no network port. The schema masterantique that owns the tables has no password at all: nobody can log in as it. And the administrator passwords were set to random values when the container was created and then thrown away. Inside the container none of that matters: docker exec ... sqlplus / as sysdba logs in as SYS through the operating system, so section 2 works right away. An application outside the container needs two extra things, both set up in minutes: its own login with a password you choose (section 3) and a network route to the database (section 4).

Every migrated user must change their password. The migration removed all passwords: password_hash and security_stamp are NULL and must_reset_password is TRUE for all 12 users. Section 7 shows a working sign-in that sends them to a password change first.

Why the username lookup looks unusual. Active usernames are unique regardless of case through a function-based index on CASE WHEN deleted_at IS NULL THEN LOWER(name) END (Oracle has no partial index). Oracle uses that index only when the query repeats its expression, as above: tested, that gives an INDEX UNIQUE SCAN on IX_USERS_NAME_ACTIVE, while LOWER(name) = LOWER('MANAGER') AND deleted_at IS NULL gives the same row through a full table scan.

Create application logins

The schema that owns the tables cannot log in, and an application should never use SYS. Create two logins once: mar_app (read and write, for the application) and mar_readonly (read only, for reports and database tools). Oracle 23ai's schema privileges grant access to every table of masterantique in one line, including tables added later. You choose both passwords; they reach SQL*Plus on standard input as substitution variables, so they never appear in a file, in your shell history, in the process list or in the output.

Save this as mar-roles.sql:

Then run it, typing each password when asked (nothing is echoed). A password may use any character except a double quote:

Check it: SELECT username FROM dba_users WHERE oracle_maintained = 'N'; (as SYS, in FREEPDB1) lists MAR_APP, MAR_READONLY and MASTERANTIQUE. Keep the mar_app password somewhere safe (a password manager, or your platform's secret store); the application reads it from the MAR_DB_PASSWORD environment variable.

The logins do not own the tables. They see them as masterantique.users, or as users after ALTER SESSION SET CURRENT_SCHEMA = masterantique. Without that, a query fails with ORA-00942: table or view "MAR_APP"."USERS" does not exist. The Spring Boot project in section 6 runs the ALTER SESSION on every new connection. Writing as mar_readonly fails with ORA-41900: missing UPDATE privilege, as it should.

Change or remove a login

The logins live with the database: they survive docker stop/start, and are lost only when the container is rebuilt with --recreate. Running mar-roles.sql a second time stops with ORA-01920: user name 'MAR_APP' conflicts with another user or role name; use ALTER USER above to change a password instead.

Choose a network route

The database container has no published port, so pick one of three ways to reach Oracle's listener on port 1521. All three were tested; none of them changes the database container itself. Oracle JDBC URLs name the service (FREEPDB1), not a database.

Route A

Container address

Quickest. Linux with Docker Engine only (not Docker Desktop). The address can change after a restart.

jdbc:oracle:thin:@//172.17.0.x:1521/FREEPDB1
Route B

App in a container

For an application that runs in Docker. Stable: reach the database by its container name.

jdbc:oracle:thin:@//mar-oracle:1521/FREEPDB1
Route C

localhost port

For an IDE or an app on your machine. A small proxy container listens on 127.0.0.1 only. Works on Docker Desktop too. The defaults in this guide assume it.

jdbc:oracle:thin:@//localhost:1522/FREEPDB1

Route A: the container's address

That prints something like 172.17.0.6; connect to it on port 1521. Use this exact form of the command: once the container joins a second network (route B or C), the shorter {{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}} prints two addresses run together.

Route B: an application container on a shared network

-e MAR_DB_PASSWORD without a value passes on the variable already set in your shell, so the password is not written on the command line.

Route C: a localhost-only port through a proxy

Needs the mar-net network from route B (the first two lines). Then start a tiny socat proxy that publishes port 1522 on 127.0.0.1 only, so nothing on your network can reach it:

Port 1522 leaves 1521 free for a locally installed Oracle. If 1522 is taken on your machine, use another (for example 127.0.0.1:1523:1521) and set MAR_DB_PORT to match. To take it all down again:

Why not publish a port on the database container? Docker cannot add a port to an existing container, and the migration tool creates it without one on purpose, so the database is never reachable from the network by accident. The proxy gives you a local port you can remove at any time without touching the data.

Two lines are Oracle-specific. connection-init-sql switches every pooled connection to the MASTERANTIQUE schema, because the login does not own the tables; that is enough for both Hibernate's schema check and plain SQL (tested; no hibernate.default_schema needed). hibernate.jdbc.fetch_size raises the Oracle driver's default of 10 rows per round trip, which Hibernate otherwise warns about at start-up.

Keep ddl-auto=validate. The schema was migrated and verified; Hibernate must only check it. update or create would change or drop the migrated tables. If validation fails, fix the entity, never the setting.

Entities

One entity per table you use. Every column is named explicitly so the mapping reads like the schema. Points that matter for this database, all confirmed by Hibernate's validation at start-up: ids are GenerationType.IDENTITY (the tables use GENERATED BY DEFAULT AS IDENTITY, and the identities already continue after the migrated ids); NUMBER(10) columns map to Integer/int; Oracle 23ai's native BOOLEAN columns map to boolean; TIMESTAMP(3) columns are LocalDateTime (no time zone, stored exactly as the legacy system had them); tickets.state is the enum's position 0, 1, 2. The three CLOB columns (password_hash, security_stamp, phone_number) need @Lob: without it Hibernate expects a VARCHAR2 and validation fails.

Repositories

The username lookup repeats the expression of the index ix_users_name_active ON users (CASE WHEN deleted_at IS NULL THEN LOWER(name) END). That is correct (it ignores case and soft-deleted users, whose expression is NULL) and fast (Oracle uses the index only for its own expression). A plain name = :name would miss Manager for manager, because Oracle compares text case-sensitively, unlike the legacy SQL Server. Hibernate sends it as where case when au1_0.deleted_at is null then lower(au1_0.name) end=lower(?).

First login: change password

The migration deliberately carried no passwords over: the legacy PBKDF2 hashes were removed and every account is marked must_reset_password = TRUE. So the first thing any sign-in meets is “you must change your password”. This mock-up shows the whole flow against the real table; the Java code is the same as for PostgreSQL.

  1. 1
    Sign in. The username is looked up ignoring case among active users. The account has no password yet, so the answer is MUST_CHANGE_PASSWORD, whatever was typed.
  2. 2
    Prove who you are. With no old password to check, the user enters a one-time code (in a real system: issued by a manager, or a link sent to a verified email address). The demo accepts one fixed code.
  3. 3
    Choose a password. Typed twice, at least 12 characters, must not contain the username.
  4. 4
    Saved. The hash is stored in the CLOB as {bcrypt}$2a$10$…, must_reset_password becomes FALSE, a new security_stamp is set and failed attempts reset. The event is logged; the password never is.
  5. 5
    Sign in normally. Right password OK; wrong password or unknown user INVALID (the same answer for both, so usernames cannot be probed).

Before this goes near production:

  • Replace DemoIdentityCheck with a real check: a single-use, expiring code a manager issues, or an emailed reset link. (Every email in the migrated data is NULL, so email resets need addresses collected first.)
  • Write the password change to the audit trail as an event (user id, time, action), never the password, in the same style as the legacy audit_logs.
  • Add lockout on repeated failures (access_failed_count, lockout_end_date_utc already exist) and rate limiting at the sign-in endpoint.
  • In a web application, the same LoginService sits behind Spring Security's authentication; the forced change becomes a redirect to a change-password page until must_reset_password is false.

Troubleshooting

Every message below was produced on the test copy.

You seeCause and fix
ORA-12541: Cannot connect. No listener at host localhost port 1522.No route. Route C: is mar-oracle-proxy running (docker ps)? Is MAR_DB_PORT the proxy's port? Is mar-oracle running and finished starting (docker logs)?
Connection times out on 172.17.0.xRoute A works only with Docker Engine on Linux; on Docker Desktop (Mac, Windows) use route C. Or the address changed after a restart: run the docker inspect command again.
ORA-01017: invalid credential or not authorized; logon deniedWrong password, or MAR_DB_PASSWORD is not set in this shell (echo ${MAR_DB_PASSWORD:+set}). Or the container was rebuilt and the logins are gone: repeat section 3.
ORA-12514: Cannot connect to database (service not known)The URL names the wrong service. It is FREEPDB1, after a slash: @//host:port/FREEPDB1. masterantique is a schema, not a service.
ORA-00942: table or view "MAR_APP"."USERS" does not existThe session is not in the masterantique schema. Run ALTER SESSION SET CURRENT_SCHEMA = masterantique, or write masterantique.users; in Spring Boot, check the connection-init-sql line.
ORA-41900: missing UPDATE privilege on "MASTERANTIQUE"."TICKETS"Writing as mar_readonly. Use mar_app for writes.
Schema validation: missing column [entity_id] in table [audit_logs]An entity field names a column the table does not have. Compare with DESCRIBE audit_logs and fix the @Column(name = ...). Never switch ddl-auto away from validate.
ORA-01920: user name 'MAR_APP' conflicts with another user or role nameThe logins script has already run. Use ALTER USER ... IDENTIFIED BY to change the password.
Enter value for ...: and SQL*Plus seems to hangAn & in your SQL was taken as a substitution variable. Run SET DEFINE OFF first (keep it on only for mar-roles.sql, which uses &app_pw on purpose).
A change you tried "just to see" was savedSQL*Plus commits on EXIT. SET EXITCOMMIT OFF, or ROLLBACK before leaving.
A username is not found although it existsCompare with CASE WHEN deleted_at IS NULL THEN LOWER(name) END = LOWER(:input); Oracle compares text case-sensitively, unlike the legacy SQL Server.
ORA-12899: value too large for column on text under 2,000 charactersThis database has MAX_STRING_SIZE = STANDARD: a VARCHAR2(2000 CHAR) value is also limited to 4,000 bytes, so about 1,333 characters of three-byte text (such as €) is the most that fits. Validate lengths in bytes before saving.
Times look shifted by some hoursColumns are TIMESTAMP(3) without time zone, read as LocalDateTime with no conversion. Whether the legacy system stored UTC or local time is unknown; do not convert until that is decided.

Reference

Tables and columns

From the migration record. Key: PK primary key, id = identity column, FK references another table.

Indexes worth knowing

  • ix_users_name_active: unique, function-based, on CASE WHEN deleted_at IS NULL THEN LOWER(name) END. Active usernames are unique ignoring case; a soft-deleted user's key is NULL and not stored, so the name can be reused and two deleted users may share it.
  • ix_roles_name: unique, case-sensitive, on roles.name (Customer, Employee, Manager).
  • One plain index on every foreign key column.
