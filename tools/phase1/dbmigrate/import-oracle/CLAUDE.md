# import-oracle — instructions for Claude Code (Linux)

**Status: SKELETON.** This folder holds the input files and these directions; the tool itself (`ingest.sh`, `verify.sql`, the report,
the self-test) is **not built yet**. The first time the user types **`Run import-oracle`** on the Linux machine, that is a **build run**:
you build the tool from the directions below, load the files into Oracle, verify them, and report. After a successful build run,
rewrite this file into the run-and-maintain shape of `tools/phase1/dbmigrate/import-postgresql/CLAUDE.md` (rules, run, settings,
layout, how load/verify/selftest/report work, input contract, testing, known limits), keeping the Oracle facts you confirmed and
dropping this "build" text. Keep it current-state; git holds the history.

**What this tool is:** it loads the Oracle export written by export-oracle (`tools/phase1/dbmigrate/export-oracle/`) into an Oracle
AI Database 26ai Free container on Linux and verifies the database against the export's record of the source. It is a proof of
concept alongside PostgreSQL (Phase 2 stays on PostgreSQL); the PostgreSQL pair is the finished model to copy the design from. The
human description is `docs/phase1/dbmigrate/import-oracle/README.md`; the strategy and security policy is
`docs/phase1/dbmigrate/DATA_MIGRATION.md` (§5 security, §10 the Oracle decisions).

## Read first, in this order

1. `tools/phase1/dbmigrate/import-postgresql/CLAUDE.md` and its `ingest.sh`, `verify.sql`, `report.sql`: the template. Reuse its structure,
   its rules, its check categories, its self-test and its exit codes; translate the database-specific parts to Oracle.
2. `docs/phase1/dbmigrate/DATA_MIGRATION.md`: §5 (security) and §10 (Oracle decisions).
3. `tools/phase1/dbmigrate/export-oracle/CLAUDE.md`: the dialect rules, the metadata contract (differences from PostgreSQL's), and the
   section **"Unverified until import-oracle has run"**: every point on that list is yours to test, and you report each as confirmed
   or corrected.
4. The three input files, in `input/`:
   - `input/01-schema.sql`: SQL*Plus script; `WHENEVER SQLERROR EXIT FAILURE`, `SET DEFINE OFF`, eight `CREATE TABLE` in dependency
     order (roles, users, audit_logs, tickets, comments, user_claims, user_logins, user_roles) with named constraints, then eleven
     `CREATE [UNIQUE] INDEX`, including the function-based `ix_users_name_active`. No `COMMIT` (DDL commits by itself).
   - `input/02-data-sanitized.sql`: SQL*Plus script; multi-row `INSERT ... VALUES` for 155 rows, pure ASCII (strings are `'...'`,
     `CHR(n)`, `UNISTR('\XXXX')` pieces joined by `||`), one `COMMIT;`, then five `ALTER TABLE ... MODIFY (id GENERATED BY DEFAULT AS
     IDENTITY (RESTART START WITH n))`.
   - `input/source-metadata.json`: the record of the source: per table `targetName`, `rowCount`, `identityLast`, `rowSha256`, `columns[]`
     (`kind`, `dataType`, `maxLength`, `precision`, `scale`, `nullable`, `default`, `identity`), `primaryKey`, `foreignKeys`, `indexes`;
     `summaries[]` (ten business questions with `expectedRows`); `expectations`; `renameMap`; `knownDifferences`; `meta`
     (`schemaSha256`, `dataSha256`, `minOracleVersion` 23). Target names are lowercase; Oracle's dictionary holds them in upper case.

## Rules (carried over from import-postgresql)

1. **Never edit `input/` by hand.** To refresh it, the user re-runs export-oracle on Windows (`Run export-oracle`) and copies all three files.
2. **Never fix rendering bugs here.** If the SQL fails to load or a hash disagrees because of how the SQL was written, stop, name the
   statement, say which rule in `tools/phase1/dbmigrate/export-oracle/migration/dialects/oracle.ps1` must change, and let the user re-run
   the export. Do not patch the SQL or `input/`.
3. **Never test on the delivered database.** The delivered container is `mar-oracle`; testing uses another container through `--config`.
4. **No secrets.** No password in git, in a file left behind, in the process list, or in the output. The tool should never need one (see
   "Container and passwords").
5. **Nothing executable comes from a data file.** Build every query yourself from names taken from the metadata after validating them
   (`^[a-z][a-z0-9_]*$`; `DBMS_ASSERT.SIMPLE_SQL_NAME`); never run text from the JSON.
6. **Generated files are never edited by hand**: `verification-results.json`, `selftest-results.json`, the HTML report.
7. **Keep LF line endings** (`.gitattributes`): the metadata records hashes of the LF form, and bash breaks on CRLF.
8. **No commit and no git command that changes anything.** The user reviews `git status` and commits.
9. **Only bash and Docker on the host** (plus `sha256sum`, `grep`, `sed`, `awk`): `sqlplus` runs inside the container, as `psql` does
   in import-postgresql. No Python, no Java, no host Oracle client.

## Environment

Linux machine with Docker Engine, bash, `sha256sum`. Containers: `mar-oracle` (delivered; no published port, no volume; `docker rm -f -v` deletes
it) and `mar-oracle-selftest` (temporary). The Oracle Free edition has hard limits (about 2 CPU threads, 2 GB RAM, 12 GB data); the data here
is a few hundred KB.

**Image and facts to verify first** (written from memory; confirm each, write what you find into the rewritten file):
- image: `container-registry.oracle.com/database/free` (official) or `gvenzl/oracle-free` (community; its `-slim` / `-faststart` tags start
  faster). Which tag is Oracle AI Database 26ai? Does pulling need a login? Pin the tag you use in `ingest.conf.example`.
- service name of the pluggable database (`FREEPDB1`), the log line that says the database is ready, and what `select banner_full from v$version`
  prints (expect "Oracle AI Database 26ai Free Release 23.26...").
- first start creates the database: allow minutes; wait until `select 1 from dual` succeeds twice in a row, not merely until the port opens.
- `sqlplus` (and whether `sqlcl`) is inside the image; its path; run it as the `oracle` OS user.
- `NLS_CHARACTERSET` (expect `AL32UTF8`), `MAX_STRING_SIZE` (`STANDARD` or `EXTENDED`), `NLS_LENGTH_SEMANTICS`, default tablespace.

## Container and passwords

The images create `SYS`/`SYSTEM` with a password from an environment variable (`ORACLE_PWD`, or `ORACLE_PASSWORD` / `ORACLE_RANDOM_PASSWORD` in
the community image), and `docker inspect` shows environment variables; import-postgresql avoided that with `POSTGRES_PASSWORD_FILE`. Find the
way that keeps rule 4, in this order of preference, and record the choice:
1. a random-password option of the image, if it has one; then never use that password;
2. a `_FILE` variant of the variable, if the image supports it;
3. a throwaway bootstrap password that is changed at once to a random value that is discarded (`ALTER USER SYS IDENTIFIED BY ...`, fed from stdin
   inside the container), so the value `docker inspect` shows is already dead. State this honestly as the documented exception.

**The tool itself should never need a password:** inside the container, `docker exec -i mar-oracle sqlplus -S / as sysdba` uses operating-system
authentication as the `oracle` user (the equivalent of PostgreSQL's trusted local socket). Then `ALTER SESSION SET CONTAINER = FREEPDB1`. Create
the application schema as a **schema-only account** (`CREATE USER masterantique NO AUTHENTICATION QUOTA UNLIMITED ON USERS`) and run the scripts
in it with `ALTER SESSION SET CURRENT_SCHEMA = masterantique`, so no application password exists at all (confirm that `CREATE TABLE` and `CREATE INDEX`
without a schema prefix land in that schema when run as `SYS`, or grant the user `CREATE TABLE` and switch to it another way). Application logins with passwords are a separate step, like `mar-roles.sql` in import-postgresql's guide (not part of this build).
Remember that as `SYS` with `CURRENT_SCHEMA` set, the `USER_*` dictionary views still describe `SYS`: use `DBA_*` (or `ALL_*`) views filtered by
`OWNER = 'MASTERANTIQUE'`.

## Build plan

Build `ingest.sh` with the same commands and exit codes as import-postgresql: `load [--recreate]`, `verify [--db <pdb>] [--out <path>]`,
`selftest`, `report`, `all [--recreate]`, `--config <path>`; exit 0 ok, 1 differences, 2 configuration/tool/Docker error, 3 refused (container
exists, no `--recreate`). Settings in `ingest.conf.example` (`CONTAINER`, `ORA_IMAGE`, `ORA_PDB`, `ORA_USER`, `INPUT_DIR`); values must match
`^[A-Za-z0-9_.:/-]+$`.

### 1. load

1. `docker info` must succeed, else exit 2.
2. **Transfer integrity before anything starts:** `sha256sum` of both SQL files must equal `schemaSha256` and `dataSha256` in the metadata (read
   with `grep -o`, no `jq`); a mismatch exits 2 and no container is created.
3. Existing container: exit 3, or with `--recreate` `docker rm -f -v`.
4. Pull the image only if missing; create and start the container with no `-p`; wait for readiness (see Environment); refuse a server whose
   `v$version` is older than 23 (`minOracleVersion`) or whose character set is not `AL32UTF8`.
5. Create the schema-only user and run `input/01-schema.sql` then `input/02-data-sanitized.sql` inside the container through `sqlplus -S`, with
   the files copied in by `docker cp` (never through a host path that a shell could rewrite). The scripts begin with `WHENEVER SQLERROR EXIT
   FAILURE`; on error exit 2 and **leave the container for inspection** (DDL cannot be rolled back, so there is nothing to undo).
6. Print row counts per table, then `LOAD COMPLETE`.

### 2. verify

Write `verify.sql` (PL/SQL, run through `sqlplus`) that reads the metadata and checks the loaded database, printing one `PASS|FAIL  category
name -- detail` line per check and writing `verification-results.json` in the same shape as import-postgresql's (so the report generator can be
shared in spirit). A missing or extra object is a FAIL, not a crash: wrap every group in an exception handler. Mirror the categories:

| Category | What is checked |
|---|---|
| environment | server version ≥ `minOracleVersion`; `AL32UTF8`; `MAX_STRING_SIZE` reported; metadata `schemaVersion` 1 |
| integrity | host SHA-256 of each SQL file = metadata |
| counts, hashes | per table `count(*)` and the canonical content hash (below) equal `rowCount` / `rowSha256`; total 155 |
| schema | exact set of tables; per table columns in order (name, `DATA_TYPE`, `CHAR_LENGTH`/precision/scale, nullability, default, identity `BY DEFAULT`); primary key; foreign keys (name, columns, target, `DELETE_RULE`: `NO ACTION` for the omitted clause); indexes (unique; the function-based expression of `ix_users_name_active` from `DBA_IND_EXPRESSIONS`, which shows upper-case quoted names); no `UNUSABLE` index; constraint names `pk_<table>` |
| summaries | ten Oracle queries keyed by the metadata's summary names, rows sorted in byte order, compared with `expectedRows`; a missing or extra query fails |
| sanitization | `sanitizeCredentials`; user count 12; no password hash or security stamp, every user `must_reset_password`; no two active usernames equal ignoring case |
| rules | see below |

**Canonical content hash (the hard part).** It must equal `rowSha256` byte for byte: per row, cells joined by `|` in column order; NULL `~`; `i:` decimal
for `NUMBER`; `b:1` / `b:0` for `BOOLEAN` (`CASE WHEN c THEN '1' WHEN NOT c THEN '0' END`, so NULL stays `~`); `t:` + `TO_CHAR(ts, 'YYYY-MM-DD
HH24:MI:SS.FF3')`; `s:` + lowercase hex of the UTF-8 bytes (`LOWER(RAWTOHEX(UTL_RAW.CAST_TO_RAW(x)))`, in PL/SQL because of SQL's 4000-byte limit; for a
`CLOB` read it in pieces); rows sorted by their own canonical text in byte order (`NLS_SORT=BINARY`, all text is ASCII); joined by LF; SHA-256
lowercase hex; an empty table hashes the empty string (`e3b0c442…`). `LISTAGG` overflows, so aggregate into a `CLOB` in PL/SQL and hash with
`DBMS_CRYPTO.HASH(clob, DBMS_CRYPTO.HASH_SH256)` (needs `EXECUTE` on `DBMS_CRYPTO`, granted by `SYS`) or test whether `STANDARD_HASH` accepts a
`CLOB`. Sanitized credential columns are NULL in the database, so they hash as `~`. **Never compare against a value the loaded database itself
produced**; only against the metadata.

**Reading the metadata inside the database, no `jq`:** `docker cp` the JSON into the container, create a directory object as `SYS`, load it with
`DBMS_LOB.LOADCLOBFROMFILE` into a PL/SQL `CLOB`, and use `JSON_TABLE` / `JSON_OBJECT_T` (native JSON). Remove the directory object and the
copied file afterwards.

**Rules group** (mirror import-postgresql's ten): (a) **first**, each identity's next value equals `identityLast + 1`, read without consuming a
value (`DBA_TAB_IDENTITY_COLS.SEQUENCE_NAME` then `DBA_SEQUENCES.LAST_NUMBER`; the sequence has a cache, so confirm what `LAST_NUMBER` means right
after `RESTART START WITH` — if it is wrong, try the `START WITH LIMIT VALUE` fallback in `export-oracle` and report); (b) then the behaviour
tests, each inside a `SAVEPOINT` and ended by `ROLLBACK TO` / a private error (`RAISE_APPLICATION_ERROR(-20999, ...)`), using explicit ids ≥
1000001 (an identity sequence is never rolled back), no DDL inside (DDL commits): an upper-case duplicate of an active username is rejected
(`ORA-00001`); a soft-deleted username can be reused; an orphan comment is rejected (`ORA-02291`); a `BOOLEAN` column rejects a value that is not a
boolean (find one that really fails, since a number is silently converted); (c) **last**, no test rows remain and no sequence moved.

### 3. selftest

On the temporary container `mar-oracle-selftest` (never the delivered one): two fresh loads give identical results (JSON compared without the
run-time lines); the delivered database gives the same check lines; a damaged copy (one comment edited, last ticket deleted,
`ix_users_name_active` dropped — copy the schema with `CREATE PLUGGABLE DATABASE ... FROM` or load a second schema user) makes verify exit 1 naming
tickets, comments, the users index and the case rule; a zeroed `rowSha256` for roles gives exactly one failure; one changed byte in the data file makes `load` exit 2 before any container exists; `load`
without `--recreate` exits 3; `DOCKER_HOST=unix:///nonexistent/docker.sock` gives exit 2. Write `selftest-results.json` (no timestamps).

### 4. report

Self-contained HTML to `docs/phase1/dbmigrate/import-oracle/MigrationVerificationReport.html`, generated from the two results files (light/dark,
phone width, byte-identical for identical input). Reuse import-postgresql's `report.sql` approach (a database as the template engine) or plain
bash; either must need nothing but bash and Docker.

## Oracle traps to test on purpose

Report a confirmed / corrected line for each of these (and for the "Unverified" list in export-oracle's `CLAUDE.md`):
- identifiers are stored upper case and the unquoted lowercase names in the SQL resolve; the names `timestamp`, `action`, `state`, `text`,
  `name`, `description` work as unquoted column names; `V$RESERVED_WORDS` marks none of the names in the schema as reserved (`RESERVED = 'Y'`);
- `BOOLEAN`, `DEFAULT FALSE NOT NULL` (the order Oracle needs), multi-row `INSERT ... VALUES` and `TIMESTAMP(3)` literals load;
- the `CHR(n)` / `UNISTR('\XXXX')` strings round-trip: a stored comment with a quote, backslash, `&`, line break, accented letter and an emoji
  comes back identical (hash equal); `SET DEFINE OFF` really stops `&` prompts; no line of the scripts trips the SQL*Plus input limit;
- `''` becomes NULL (export-oracle refuses empty strings, so verify that none slipped in: `count(*)` of NULLs in the nullable text columns equals
  the metadata's);
- `VARCHAR2(2000 CHAR)` with `MAX_STRING_SIZE=STANDARD`: is a 2,000-character value with multi-byte characters accepted? Record the finding and the
  setting in the report;
- DDL commits by itself: a failed load leaves objects behind (the container is kept; `--recreate` cleans up);
- the function-based unique index treats soft-deleted rows as absent (two soft-deleted users with the same name are allowed) and rejects
  `Bob` / `bob` when both are active.

2. Update `docs/phase1/dbmigrate/import-oracle/README.md` (latest results) and `tools/phase1/dbmigrate/import-oracle/README.md`; add a short

3. If a rendering rule was wrong: do **not** fix it here. List the corrections for `oracle.ps1` (statement, error, proposed fix) so the user can
   re-run `Run export-oracle` on Windows and hand the new files off; then repeat the load.
4. Rewrite this `CLAUDE.md` (see the top). Do not commit.

## Known limits (expected)

- Verification is against the export's record, not the live SQL Server; it catches mistakes, not tampering.
- Oracle 23ai or later only (`BOOLEAN`, multi-row `INSERT`); not 19c.
- Timestamps carry no time zone and the source zone is unknown; no conversion is made.
- Usernames are case-insensitive only through the function-based index; applications must compare `LOWER(name) = LOWER(:input)`.
- The input files contain sanitized but real project data (usernames, timestamps, comment text).
