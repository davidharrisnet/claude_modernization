## 3. What was built

1. **`dialects/postgres.ps1`**: renders PostgreSQL 15+ SQL from the same in-memory model the earlier dialects use. It holds the explicit snake_case rename map for every table, column, foreign key and index and **fails on any name that is not in the map**, so a new source column is never silently renamed differently. Mapping: identity primary key to `INTEGER GENERATED BY DEFAULT AS IDENTITY`, `bit` to `BOOLEAN`, `datetime` to `TIMESTAMP` (no time zone; literals with 3 fractional digits; the tool refuses to drop real sub-millisecond precision), `nvarchar(n)` to `VARCHAR(n)`, `nvarchar(max)` to `TEXT`. The soft-delete filtered unique index becomes `CREATE UNIQUE INDEX ix_users_name_active ON users (lower(name)) WHERE deleted_at IS NULL`; `roles.name` gets a plain case-sensitive unique index. Carriage returns and other control characters in text values are written as `chr(n)` so git line-ending conversion cannot alter data.
2. **`Metadata.ps1`**: writes `source-metadata.json` from the catalog and the same in-memory rows the SQL is rendered from (after sanitizing).
3. **`Export.ps1`**: sanitizes in memory, then renders. It **refuses to run** with `sanitizeCredentials` off, so an unsanitized file can never be produced by this tool.
4. **`SelfTest.ps1`**: five self-tests (section 5).
5. **`Report.ps1` / `ExportReport.ps1`**: the Word export report, built from the metadata only.
6. **`.gitattributes`** in the iteration folder: `*.sql`, `*.json` and `*.md` are pinned to LF, because the metadata records SHA-256 hashes of the LF form and string literals can contain raw LF.

## 4. The export, step by step

```
tools\phase1\dbmigrate\iteration4\dbmigrate4.cmd all --target postgres
```

Runs `export`, `selftest` and `report` (each can be run alone). Exit code 0.

1. **Export.** Reads the SQL Server catalog and every row; converts each value to one text form; blanks `PasswordHash` and `SecurityStamp` and adds `MustResetPassword = 1` for the 12 users, in memory; renders the two SQL files; writes the metadata. Output above.
2. **Self-test** (section 5).
3. **Report.** `MigrationExportReport4.docx` from `source-metadata.json`; 15 package parts, every XML part well-formed, 5 images all referenced. The banner reads EXPORT COMPLETE.

### The generated SQL was proven to load, once, during the build

Windows cannot prove that PostgreSQL accepts the SQL, and iteration 4 has no PostgreSQL. The formal proof is iteration 5, on Linux. Because that tool does not exist yet, the SQL was checked once during the build with a throwaway `postgres:16` container (16.15, UTF-8) on this machine; the container was removed afterwards and is **not part of the deliverable**. Results:

- `psql -v ON_ERROR_STOP=1 -f 01-schema.sql -f 02-data-sanitized.sql` succeeded with no errors (`COMMIT`).
- All 8 table counts matched the export (3, 12, 78, 24, 26, 0, 0, 12).
- **All 8 canonical table hashes recomputed inside PostgreSQL matched the ones the export recorded.** A dynamic PL/pgSQL block read the metadata JSON (`\set meta` plus `jsonb`), built each query from the column list, and compared. This proves the canonical form is implementable independently on both sides and that the metadata design for iteration 5 works.
- Rule tests, in a rolled-back transaction, all passed: a second active user differing only by case (`MANAGER` vs `manager`) is rejected; a soft-deleted username can be reused (stored as typed); an orphan foreign key is rejected; a duplicate role name is rejected.
- The partial expression index is `CREATE UNIQUE INDEX ix_users_name_active ON public.users USING btree (lower((name)::text)) WHERE (deleted_at IS NULL)`.
- The column names `timestamp`, `text`, `action`, `state`, `name` and `description` work unquoted on PostgreSQL 16.

## 6. Problems met and decisions taken during the build

| Point | What happened | Resolution |
|---|---|---|
| `nextval` is not rolled back | The rule tests inserted rows using the identity default; even though the transaction was rolled back, the sequences advanced (`users_id_seq` 12 to 14, `comments_id_seq` 26 to 27). | Recorded in `ITERATION5_PLAN.md`: check sequence state first, and give every rule-test insert an explicit high id, which `GENERATED BY DEFAULT` accepts without touching the sequence. |
| Row order in the canonical hash | The plan said "primary-key order". A string primary key would sort differently in SQL Server and PostgreSQL (collations). | Built and documented: rows are sorted by their own canonical text (ordinal/byte order; `COLLATE "C"` in SQL). No primary-key or collation knowledge is needed. |
| Git commit in the metadata | Recording the tooling commit in `meta` would make the metadata differ after every commit. | The commit moved into the separate `run` section with the run time; the determinism test ignores that section. |
| `RepoRoot` depth | The plan expected to have to fix it after copying. | Iteration 2's depth was already correct for `iteration4\migration\`; no change. |
| Trimmed helper file | After pruning iteration 2's `Common.ps1`, `Get-Dialect` was missing. | Restored before the first run. |

## 7. Known differences and limitations

- Identifiers are lowercase snake_case, and foreign key and index names were renamed too. Data values are never lowercased. This is a naming difference from the legacy schema, not a data change.
- `datetime` columns become `TIMESTAMP` without time zone, values stored exactly as in the source. **It is not known whether the legacy application stored UTC or local times** (only `LockoutEndDateUtc` is UTC by name), so no conversion was made. Phase 2 must decide the zone.
- SQL Server compared text case-insensitively; PostgreSQL does not. Username uniqueness is case-insensitive through the `lower(name)` index, so **Phase 2 authentication must compare `lower(name) = lower(:input)`**. Usernames are stored as typed.
- The metadata is a record produced by the same run; anyone with write access could edit both it and the SQL. It guards against mistakes, not tampering.
- The export files still contain real project data (usernames, timestamps, comment text), but no credentials.
- The Word report was checked structurally (valid package, well-formed XML, images referenced) and rebuilds byte-identically; it was not rendered page by page in Word.

Exit codes: 0 success, 1 self-test differences, 2 configuration or tool error (including a refusal to export unsanitized data), 3 refused. See `tools\phase1\dbmigrate\iteration4\README.md`.

## 10. Conclusion

The SQL Server database was exported by a repeatable script into sanitized PostgreSQL schema and data files with a source-metadata record, all 155 rows and no credentials. The export is deterministic, its row counts match a live count of the source, and the generated SQL loaded into a real PostgreSQL 16 with matching counts, matching content hashes and working rules. Iteration 4 meets its plan; the formal load and verification are iteration 5's job.
