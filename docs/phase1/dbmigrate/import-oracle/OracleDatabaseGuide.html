MasterAntiqueRepair · database migration · import-oracle (proof of concept)

Connecting to the MasterAntiqueRepair Oracle database

The migrated database runs in an Oracle AI Database 26ai Free container on the Linux machine. This guide takes you from a first query in SQL*Plus to a Spring Boot 4.1.1 application that reads it with JDBC and JPA, including the password change every migrated user is forced to make on first login. Every command and file here was run against a copy of this database before it was written down. Phase 2 uses the PostgreSQL database; this is the same path shown for Oracle.

At a glance

The tables hold 12 users (1 manager, 3 employees, 8 customers), 24 repair tickets (8 each SUBMITTED, INPROGRESS, COMPLETED), 26 comments, 78 audit log rows and 12 user-role links. Names are lowercase snake_case in the SQL (created_at, user_id) and unquoted, so Oracle stores them in upper case and you can write them in any case without quotes; never write them in double quotes in lower case ("users" does not exist).

Three things are locked down on purpose. The container publishes no network port. The schema masterantique that owns the tables has no password at all: nobody can log in as it. And the administrator passwords were set to random values when the container was created and then thrown away. Inside the container none of that matters: docker exec ... sqlplus / as sysdba logs in as SYS through the operating system, so section 2 works right away. An application outside the container needs two extra things, both set up in minutes: its own login with a password you choose (section 3) and a network route to the database (section 4).

Every migrated user must change their password. The migration removed all passwords: password_hash and security_stamp are NULL and must_reset_password is TRUE for all 12 users. Section 7 shows a working sign-in that sends them to a password change first.

Connect from a terminal

No setup, no password. Open an interactive SQL*Plus session inside the container, then switch to the pluggable database and to the migrated schema:

bash
docker exec -it mar-oracle sqlplus / as sysdba
sql
ALTER SESSION SET CONTAINER = FREEPDB1;
ALTER SESSION SET CURRENT_SCHEMA = masterantique;

You get the SQL> prompt. Type EXIT to leave. SYS can change anything, so for looking around prefer the read-only login from section 3 once it exists: docker exec -it mar-oracle sqlplus mar_readonly@//localhost:1521/FREEPDB1 (it asks for the password), then the CURRENT_SCHEMA line. One-off queries and scripts

SQL*Plus reads statements from standard input, so a one-off query is a pipe (-S silent, headings and feedback off):

bash
printf 'SET HEADING OFF FEEDBACK OFF\nALTER SESSION SET CONTAINER = FREEPDB1;\nSELECT COUNT(*) FROM masterantique.tickets;\n' |
  docker exec -i mar-oracle sqlplus -S / as sysdba
Output
        24

Run a whole SQL file from your machine by piping it in (-i keeps standard input open):

bash
docker exec -i mar-oracle sqlplus -S / as sysdba < queries.sql

Sample queries

Save these as queries.sql and run them as above, or paste them at the prompt. The first lines set up the session and the output format.

queries.sql
-- queries.sql: sample queries on the migrated MasterAntiqueRepair data (SQL*Plus).
SET LINESIZE 160 PAGESIZE 100 TAB OFF FEEDBACK OFF
ALTER SESSION SET CONTAINER = FREEPDB1;
ALTER SESSION SET CURRENT_SCHEMA = masterantique;
ALTER SESSION SET NLS_TIMESTAMP_FORMAT = 'YYYY-MM-DD HH24:MI:SS.FF3';
SET FEEDBACK ON
COLUMN name FORMAT A12
COLUMN customer FORMAT A12
COLUMN employee FORMAT A12
COLUMN discriminator FORMAT A13
COLUMN workflow_state FORMAT A14
COLUMN description FORMAT A50
COLUMN text FORMAT A60
COLUMN created_at FORMAT A23
COLUMN timestamp FORMAT A23

-- Users by type (customers, employees, managers share one table)
SELECT discriminator, COUNT(*) FROM users GROUP BY discriminator ORDER BY discriminator;

-- Tickets by workflow state (0 SUBMITTED, 1 INPROGRESS, 2 COMPLETED)
SELECT state,
       CASE state WHEN 0 THEN 'SUBMITTED' WHEN 1 THEN 'INPROGRESS' WHEN 2 THEN 'COMPLETED' END AS workflow_state,
       COUNT(*)
FROM tickets GROUP BY state ORDER BY state;

-- Open tickets with customer and assigned employee
SELECT t.id, c.name AS customer, e.name AS employee, SUBSTR(t.description, 1, 50) AS description
FROM tickets t
JOIN users c ON c.id = t.customer_id
LEFT JOIN users e ON e.id = t.user_id
WHERE t.state <> 2
ORDER BY t.id
FETCH FIRST 5 ROWS ONLY;

-- Comments on one ticket, oldest first
SELECT cm.created_at, u.name, cm.text
FROM comments cm JOIN users u ON u.id = cm.user_id
WHERE cm.ticket_id = 1
ORDER BY cm.created_at;

-- Latest audit events
SELECT a.timestamp, u.name, a.action, a.entity_type, a.entity_id
FROM audit_logs a JOIN users u ON u.id = a.user_id
ORDER BY a.timestamp DESC
FETCH FIRST 5 ROWS ONLY;

-- Case-insensitive username lookup, the way sign-in must do it: the condition repeats the expression of the index
-- ix_users_name_active, so Oracle uses it (and soft-deleted users, whose expression is NULL, never match)
SELECT id, name, discriminator, must_reset_password
FROM users WHERE CASE WHEN deleted_at IS NULL THEN LOWER(name) END = LOWER('MANAGER');

Part of the output:

Output
     STATE WORKFLOW_STATE   COUNT(*)
---------- -------------- ----------
         0 SUBMITTED               8

---------- ------------ ------------- -----------
         1 manager      Manager       TRUE

Why the username lookup looks unusual. Active usernames are unique regardless of case through a function-based index on CASE WHEN deleted_at IS NULL THEN LOWER(name) END (Oracle has no partial index). Oracle uses that index only when the query repeats its expression, as above: tested, that gives an INDEX UNIQUE SCAN on IX_USERS_NAME_ACTIVE, while LOWER(name) = LOWER('MANAGER') AND deleted_at IS NULL gives the same row through a full table scan.

Experiment safely

Changes are kept only when committed, so try things and roll them back. One Oracle trap: SQL*Plus commits pending changes when you EXIT (tested), so turn that off first, or always end with ROLLBACK.

sql
SET EXITCOMMIT OFF
UPDATE tickets SET state = 2 WHERE id = 3;
SELECT id, state FROM tickets WHERE id = 3;   -- shows 2
ROLLBACK;
SELECT id, state FROM tickets WHERE id = 3;   -- back to 0

Create application logins

The schema that owns the tables cannot log in, and an application should never use SYS. Create two logins once: mar_app (read and write, for the application) and mar_readonly (read only, for reports and database tools). Oracle 23ai's schema privileges grant access to every table of masterantique in one line, including tables added later. You choose both passwords; they reach SQL*Plus on standard input as substitution variables, so they never appear in a file, in your shell history, in the process list or in the output.

Save this as mar-roles.sql:

mar-roles.sql
-- mar-roles.sql: application logins for the MasterAntiqueRepair database. Run once, as SYS in the container.
-- The passwords arrive as the substitution variables app_pw and ro_pw, defined on standard input just before this script
-- (see the guide), never written in this file. SET VERIFY OFF keeps SQL*Plus from echoing them.
SET VERIFY OFF
WHENEVER SQLERROR EXIT FAILURE
ALTER SESSION SET CONTAINER = FREEPDB1;

-- Read/write login for the application. Schema privileges (Oracle 23ai and later) cover every table in the schema,
-- including tables added later.
CREATE USER mar_app IDENTIFIED BY "&app_pw" DEFAULT TABLESPACE users;
GRANT CREATE SESSION TO mar_app;
GRANT SELECT ANY TABLE, INSERT ANY TABLE, UPDATE ANY TABLE, DELETE ANY TABLE ON SCHEMA masterantique TO mar_app;

-- Read-only login for reports and ad-hoc tools.
CREATE USER mar_readonly IDENTIFIED BY "&ro_pw" DEFAULT TABLESPACE users;
GRANT CREATE SESSION TO mar_readonly;
GRANT SELECT ANY TABLE ON SCHEMA masterantique TO mar_readonly;
EXIT

Then run it, typing each password when asked (nothing is echoed). A password may use any character except a double quote:

bash
read -rsp 'New password for mar_app: ' APP_PW; echo
read -rsp 'New password for mar_readonly: ' RO_PW; echo
{ printf 'DEFINE app_pw = "%s"\nDEFINE ro_pw = "%s"\n' "$APP_PW" "$RO_PW"; cat mar-roles.sql; } |
  docker exec -i mar-oracle sqlplus -S / as sysdba
unset APP_PW RO_PW

Check it: SELECT username FROM dba_users WHERE oracle_maintained = 'N'; (as SYS, in FREEPDB1) lists MAR_APP, MAR_READONLY and MASTERANTIQUE. Keep the mar_app password somewhere safe (a password manager, or your platform's secret store); the application reads it from the MAR_DB_PASSWORD environment variable.

The logins do not own the tables. They see them as masterantique.users, or as users after ALTER SESSION SET CURRENT_SCHEMA = masterantique. Without that, a query fails with ORA-00942: table or view "MAR_APP"."USERS" does not exist. The Spring Boot project in section 6 runs the ALTER SESSION on every new connection. Writing as mar_readonly fails with ORA-41900: missing UPDATE privilege, as it should.

Change or remove a login

bash
read -rsp 'New password for mar_app: ' NEW_PW; echo
{ printf 'SET VERIFY OFF\nDEFINE new_pw = "%s"\n' "$NEW_PW"
  printf 'ALTER SESSION SET CONTAINER = FREEPDB1;\nALTER USER mar_app IDENTIFIED BY "&new_pw";\n'; } |
  docker exec -i mar-oracle sqlplus -S / as sysdba
unset NEW_PW

# remove a login and everything granted to it
printf 'ALTER SESSION SET CONTAINER = FREEPDB1;\nDROP USER mar_readonly CASCADE;\n' |
  docker exec -i mar-oracle sqlplus -S / as sysdba

The logins live with the database: they survive docker stop/start, and are lost only when the container is rebuilt with --recreate. Running mar-roles.sql a second time stops with ORA-01920: user name 'MAR_APP' conflicts with another user or role name; use ALTER USER above to change a password instead.

Choose a network route

The database container has no published port, so pick one of three ways to reach Oracle's listener on port 1521. All three were tested; none of them changes the database container itself. Oracle JDBC URLs name the service (FREEPDB1), not a database.

Route A

Container address

Quickest. Linux with Docker Engine only (not Docker Desktop). The address can change after a restart.

jdbc:oracle:thin:@//172.17.0.x:1521/FREEPDB1
Route B

App in a container

For an application that runs in Docker. Stable: reach the database by its container name.

jdbc:oracle:thin:@//mar-oracle:1521/FREEPDB1
Route C

localhost port

For an IDE or an app on your machine. A small proxy container listens on 127.0.0.1 only. Works on Docker Desktop too. The defaults in this guide assume it.

jdbc:oracle:thin:@//localhost:1522/FREEPDB1

Route A: the container's address

bash
docker inspect -f '{{index .NetworkSettings.Networks "bridge" "IPAddress"}}' mar-oracle

That prints something like 172.17.0.6; connect to it on port 1521. Use this exact form of the command: once the container joins a second network (route B or C), the shorter {{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}} prints two addresses run together.

Route B: an application container on a shared network

bash
docker network create mar-net
docker network connect mar-net mar-oracle

# run the Spring Boot jar from section 6 in a container on that network
docker run --rm --network mar-net \
  -v "$PWD/build/libs:/app:ro" \
  -e MAR_DB_HOST=mar-oracle -e MAR_DB_PORT=1521 -e MAR_DB_PASSWORD \
  eclipse-temurin:21-jre java -jar /app/mar-db-client-0.0.1-SNAPSHOT.jar

-e MAR_DB_PASSWORD without a value passes on the variable already set in your shell, so the password is not written on the command line.

Route C: a localhost-only port through a proxy

Needs the mar-net network from route B (the first two lines). Then start a tiny socat proxy that publishes port 1522 on 127.0.0.1 only, so nothing on your network can reach it:

bash
docker network create mar-net                  # skip if it exists
docker network connect mar-net mar-oracle      # skip if already connected

docker run -d --name mar-oracle-proxy --network mar-net \
  -p 127.0.0.1:1522:1521 \
  alpine/socat tcp-listen:1521,fork,reuseaddr tcp-connect:mar-oracle:1521

docker port mar-oracle-proxy      # 1521/tcp -> 127.0.0.1:1522

Port 1522 leaves 1521 free for a locally installed Oracle. If 1522 is taken on your machine, use another (for example 127.0.0.1:1523:1521) and set MAR_DB_PORT to match. To take it all down again:

bash
docker rm -f mar-oracle-proxy
docker network disconnect mar-net mar-oracle
docker network rm mar-net

Why not publish a port on the database container? Docker cannot add a port to an existing container, and the migration tool creates it without one on purpose, so the database is never reachable from the network by accident. The proxy gives you a local port you can remove at any time without touching the data.

Test with plain JDBC

Before bringing in Spring, prove the login and the route with one Java file and the Oracle JDBC driver (ojdbc11, the thin driver for Java 11 and later; pure Java, no Oracle client installation). Java 11 and later run a single source file directly.

JdbcSmokeTest.java
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.ResultSet;
import java.sql.Statement;
import java.util.Properties;

/**
 * The smallest possible connection test: plain JDBC, no Spring. Run it straight from source (Java 11+):
 *   MAR_DB_PASSWORD=... java -cp ojdbc11-23.26.3.0.0.jar JdbcSmokeTest.java
 */
public class JdbcSmokeTest {

    public static void main(String[] args) throws Exception {
        String host = env("MAR_DB_HOST", "localhost");
        String port = env("MAR_DB_PORT", "1522");
        String url = "jdbc:oracle:thin:@//" + host + ":" + port + "/" + env("MAR_DB_SERVICE", "FREEPDB1");

        Properties props = new Properties();
        props.setProperty("user", env("MAR_DB_USER", "mar_app"));
        props.setProperty("password", System.getenv("MAR_DB_PASSWORD"));      // required; never hard-code it
        props.setProperty("oracle.net.CONNECT_TIMEOUT", "10000");               // milliseconds

        try (Connection conn = DriverManager.getConnection(url, props);
             Statement st = conn.createStatement()) {
            // The tables belong to the schema MASTERANTIQUE, not to the login.
            st.execute("ALTER SESSION SET CURRENT_SCHEMA = MASTERANTIQUE");
            try (ResultSet rs = st.executeQuery(
                    "select (select banner from v$version where rownum = 1),"
                            + " (select count(*) from users), (select count(*) from tickets) from dual")) {
                rs.next();
                System.out.println("Connected to " + url);
                System.out.println(rs.getString(1));
                System.out.println("users=" + rs.getLong(2) + " tickets=" + rs.getLong(3));
            }
        }
    }

    private static String env(String name, String fallback) {
        String v = System.getenv(name);
        return v == null || v.isBlank() ? fallback : v;
    }
}

Two lines are Oracle-specific. connection-init-sql switches every pooled connection to the MASTERANTIQUE schema, because the login does not own the tables; that is enough for both Hibernate's schema check and plain SQL (tested; no hibernate.default_schema needed). hibernate.jdbc.fetch_size raises the Oracle driver's default of 10 rows per round trip, which Hibernate otherwise warns about at start-up.

Keep ddl-auto=validate. The schema was migrated and verified; Hibernate must only check it. update or create would change or drop the migrated tables. If validation fails, fix the entity, never the setting.

Entities

One entity per table you use. Every column is named explicitly so the mapping reads like the schema. Points that matter for this database, all confirmed by Hibernate's validation at start-up: ids are GenerationType.IDENTITY (the tables use GENERATED BY DEFAULT AS IDENTITY, and the identities already continue after the migrated ids); NUMBER(10) columns map to Integer/int; Oracle 23ai's native BOOLEAN columns map to boolean; TIMESTAMP(3) columns are LocalDateTime (no time zone, stored exactly as the legacy system had them); tickets.state is the enum's position 0, 1, 2. The three CLOB columns (password_hash, security_stamp, phone_number) need @Lob: without it Hibernate expects a VARCHAR2 and validation fails.

model/AppUser.java
package com.masterantique.dbclient.model;

import jakarta.persistence.Column;

Repositories

The username lookup repeats the expression of the index ix_users_name_active ON users (CASE WHEN deleted_at IS NULL THEN LOWER(name) END). That is correct (it ignores case and soft-deleted users, whose expression is NULL) and fast (Oracle uses the index only for its own expression). A plain name = :name would miss Manager for manager, because Oracle compares text case-sensitively, unlike the legacy SQL Server. Hibernate sends it as where case when au1_0.deleted_at is null then lower(au1_0.name) end=lower(?).

repo/AppUserRepository.java
package com.masterantique.dbclient.repo;

import com.masterantique.dbclient.model.AppUser;
import java.util.Optional;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

public interface AppUserRepository extends JpaRepository<AppUser, Integer> {

    /**
     * Sign-in lookup. Usernames are unique ignoring case among active users, enforced by the function-based index
     * ix_users_name_active ON users (CASE WHEN deleted_at IS NULL THEN LOWER(name) END). Oracle uses that index only
     * when the query repeats its expression, so the condition below is written exactly that way; it matches
     * active users only, because the expression is NULL for soft-deleted ones.
     */
    @Query("select u from AppUser u where (case when u.deletedAt is null then lower(u.name) end) = lower(:name)")
    Optional<AppUser> findActiveByName(@Param("name") String name);

    long countByDiscriminator(String discriminator);

    long countByMustResetPasswordTrue();
}

First login: change password

The migration deliberately carried no passwords over: the legacy PBKDF2 hashes were removed and every account is marked must_reset_password = TRUE. So the first thing any sign-in meets is “you must change your password”. This mock-up shows the whole flow against the real table; the Java code is the same as for PostgreSQL.

  1. 1
    Sign in. The username is looked up ignoring case among active users. The account has no password yet, so the answer is MUST_CHANGE_PASSWORD, whatever was typed.
  2. 2
    Prove who you are. With no old password to check, the user enters a one-time code (in a real system: issued by a manager, or a link sent to a verified email address). The demo accepts one fixed code.
  3. 3
    Choose a password. Typed twice, at least 12 characters, must not contain the username.
  4. 4
    Saved. The hash is stored in the CLOB as {bcrypt}$2a$10$…, must_reset_password becomes FALSE, a new security_stamp is set and failed attempts reset. The event is logged; the password never is.
  5. 5
    Sign in normally. Right password OK; wrong password or unknown user INVALID (the same answer for both, so usernames cannot be probed).

login/LoginService.java
package com.masterantique.dbclient.login;

import com.masterantique.dbclient.model.AppUser;
import com.masterantique.dbclient.repo.AppUserRepository;
import java.util.Optional;
import java.util.UUID;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/**
 * Sign-in against the migrated users table, including the forced password change every migrated user
 * meets on first login (password_hash is NULL and must_reset_password is true after the migration).
 */
@Service
public class LoginService {

    private static final Logger log = LoggerFactory.getLogger(LoginService.class);
    private static final int MIN_LENGTH = 12;

    private final AppUserRepository users;
    private final IdentityCheck identityCheck;
    // Stores "{bcrypt}$2a$10$..." so the algorithm can be changed later without breaking old hashes.
    private final PasswordEncoder encoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();
    // Compared against when the user is unknown, so both cases take about the same time.
    private final String dummyHash = encoder.encode("not-a-real-password");

    public LoginService(AppUserRepository users, IdentityCheck identityCheck) {
        this.users = users;
        this.identityCheck = identityCheck;
    }

    @Transactional(readOnly = true)
    public LoginResult login(String username, String password) {
        Optional<AppUser> found = users.findActiveByName(username);
        if (found.isEmpty()) {
            encoder.matches(password, dummyHash);
            return LoginResult.INVALID;
        }
        AppUser user = found.get();
        if (user.isMustResetPassword() || user.getPasswordHash() == null) {
            return LoginResult.MUST_CHANGE_PASSWORD;
        }
        return encoder.matches(password, user.getPasswordHash()) ? LoginResult.OK : LoginResult.INVALID;
    }

    /**
     * Sets the first password. Throws IllegalArgumentException with a message fit to show the user when the
     * identity check or the password policy fails.
     */
    @Transactional
    public void changePassword(String username, String oneTimeCode, String newPassword, String confirmPassword) {
        AppUser user = users.findActiveByName(username)
                .orElseThrow(() -> new IllegalArgumentException("Unknown or inactive user."));
        if (!identityCheck.verify(user.getName(), oneTimeCode)) {
            throw new IllegalArgumentException("The one-time code is not valid.");
        }
        checkPolicy(user.getName(), newPassword, confirmPassword);
        user.setNewPassword(encoder.encode(newPassword), UUID.randomUUID().toString());
        // Saved on commit (the entity is managed). Record the event, never the password.
        log.info("Password changed for user id {} ({}); must_reset_password cleared", user.getId(), user.getDiscriminator());
    }

    static void checkPolicy(String username, String password, String confirm) {
        if (password == null || password.length() < MIN_LENGTH) {
            throw new IllegalArgumentException("The password must have at least " + MIN_LENGTH + " characters.");
        }
        if (!password.equals(confirm)) {
            throw new IllegalArgumentException("The two passwords do not match.");
        }
        if (password.toLowerCase().contains(username.toLowerCase())) {
            throw new IllegalArgumentException("The password must not contain the username.");
        }
    }
}
login/FirstLoginDemo.java
package com.masterantique.dbclient.login;

import java.io.Console;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.CommandLineRunner;
import org.springframework.context.annotation.Profile;
import org.springframework.stereotype.Component;

/**
 * Console walk-through of a migrated user's first login. Run with --spring.profiles.active=first-login-demo.
 * Asks for the values it is not given (demo.username, demo.password, demo.one-time-code, demo.new-password),
 * hiding passwords.
 */
@Component
@Profile("first-login-demo")
public class FirstLoginDemo implements CommandLineRunner {

    private final LoginService login;
    private final String username;
    private final String firstPassword;
    private final String oneTimeCode;
    private final String newPassword;

    public FirstLoginDemo(LoginService login,
                          @Value("${demo.username:}") String username,
                          @Value("${demo.password:}") String firstPassword,
                          @Value("${demo.one-time-code:}") String oneTimeCode,
                          @Value("${demo.new-password:}") String newPassword) {
        this.login = login;
        this.username = username;
        this.firstPassword = firstPassword;
        this.oneTimeCode = oneTimeCode;
        this.newPassword = newPassword;
    }

    @Override
    public void run(String... args) {
        String user = orAsk(username, "Username: ", false);
        String password = orAsk(firstPassword, "Password: ", true);   // migrated users have none yet

        LoginResult first = login.login(user, password);
        System.out.println("1. Sign in as '" + user + "' -> " + first);
        if (first == LoginResult.OK) {
            System.out.println("   Signed in. This account already has its own password.");
            return;
        }
        if (first == LoginResult.INVALID) {
            System.out.println("   Wrong username or password.");
            return;
        }

        System.out.println("   You must change your password before you continue.");
        String code = orAsk(oneTimeCode, "   One-time code from your manager: ", false);
        String pw1 = orAsk(newPassword, "   New password (12+ characters): ", true);
        String pw2 = orAsk(newPassword, "   Repeat the new password: ", true);
        try {
            login.changePassword(user, code, pw1, pw2);
            System.out.println("2. Password changed.");
        } catch (IllegalArgumentException e) {
            System.out.println("2. Not changed: " + e.getMessage());
            return;
        }

        System.out.println("3. Sign in again with the new password -> " + login.login(user, pw1));
        System.out.println("4. Sign in with a wrong password      -> " + login.login(user, pw1 + "x"));
    }

    private static String orAsk(String given, String prompt, boolean secret) {
        if (given != null && !given.isEmpty()) {
            return given;
        }
        Console console = System.console();
        if (console == null) {
            throw new IllegalStateException("No console: pass --demo.username, --demo.one-time-code and --demo.new-password");
        }
        return secret ? new String(console.readPassword(prompt)) : console.readLine(prompt);
    }
}

Before this goes near production:

  • Replace DemoIdentityCheck with a real check: a single-use, expiring code a manager issues, or an emailed reset link. (Every email in the migrated data is NULL, so email resets need addresses collected first.)
  • Write the password change to the audit trail as an event (user id, time, action), never the password, in the same style as the legacy audit_logs.
  • Add lockout on repeated failures (access_failed_count, lockout_end_date_utc already exist) and rate limiting at the sign-in endpoint.
  • In a web application, the same LoginService sits behind Spring Security's authentication; the forced change becomes a redirect to a change-password page until must_reset_password is false.

ORA-00942: table or view "MAR_APP"."USERS" does not existThe session is not in the masterantique schema. Run ALTER SESSION SET CURRENT_SCHEMA = masterantique, or write masterantique.users; in Spring Boot, check the connection-init-sql line.
ORA-41900: missing UPDATE privilege on "MASTERANTIQUE"."TICKETS"Writing as mar_readonly. Use mar_app for writes.
Schema validation: missing column [entity_id] in table [audit_logs]An entity field names a column the table does not have. Compare with DESCRIBE audit_logs and fix the @Column(name = ...). Never switch ddl-auto away from validate.
ORA-01920: user name 'MAR_APP' conflicts with another user or role nameThe logins script has already run. Use ALTER USER ... IDENTIFIED BY to change the password.
Enter value for ...: and SQL*Plus seems to hangAn & in your SQL was taken as a substitution variable. Run SET DEFINE OFF first (keep it on only for mar-roles.sql, which uses &app_pw on purpose).
A change you tried "just to see" was savedSQL*Plus commits on EXIT. SET EXITCOMMIT OFF, or ROLLBACK before leaving.
A username is not found although it existsCompare with CASE WHEN deleted_at IS NULL THEN LOWER(name) END = LOWER(:input); Oracle compares text case-sensitively, unlike the legacy SQL Server.
ORA-12899: value too large for column on text under 2,000 charactersThis database has MAX_STRING_SIZE = STANDARD: a VARCHAR2(2000 CHAR) value is also limited to 4,000 bytes, so about 1,333 characters of three-byte text (such as €) is the most that fits. Validate lengths in bytes before saving.
Times look shifted by some hoursColumns are TIMESTAMP(3) without time zone, read as LocalDateTime with no conversion. Whether the legacy system stored UTC or local time is unknown; do not convert until that is decided.

Indexes worth knowing

  • ix_users_name_active: unique, function-based, on CASE WHEN deleted_at IS NULL THEN LOWER(name) END. Active usernames are unique ignoring case; a soft-deleted user's key is NULL and not stored, so the name can be reused and two deleted users may share it.
  • ix_roles_name: unique, case-sensitive, on roles.name (Customer, Employee, Manager).
  • One plain index on every foreign key column.
