## 1. Purpose

Take the three files iteration 4 exported on Windows (`01-schema.sql`, `02-data-sanitized.sql`, `source-metadata.json`, checked into `tools/phase1/dbmigrate/iteration5/input/`), build a fully populated **PostgreSQL** database from them inside a **Docker container** on Linux, and **verify that the database is the same as the SQL Server source it was exported from**. The Linux machine cannot reach SQL Server, so the comparison is against `source-metadata.json`, which was written on Windows by a code path separate from the one that wrote the SQL.

## 3. What was built

All in `tools/phase1/dbmigrate/iteration5/`:

1. **`ingest.sh`**: one bash script with the commands `load`, `verify`, `selftest`, `report` and `all`. Exit codes 0 ok, 1 differences, 2 error, 3 refused.
2. **`verify.sql`**: a static `psql` script. It reads the metadata as `jsonb` and builds every query itself, quoting names with `format('%I')`, so nothing executable is ever read from the JSON. It prints one PASS/FAIL line per check and writes `verification-results.json`.
3. **`report.sql`**: renders `MigrationVerificationReport5.html` from the results JSON.
4. **`ingest.conf.example`**, **`.gitattributes`** (`*.sql`, `*.json`, `*.sh`, `*.md` pinned to LF) and **`.gitignore`** (`ingest.conf`, logs), plus `README.md`.

## 4. The run, step by step

```
tools/phase1/dbmigrate/iteration5/ingest.sh all --recreate
```

1. **Load.** The SHA-256 of both SQL files matched the metadata (`67e94060...`, `301f79cf...`). The container started from `postgres:16.1`, the tool waited for the image's first-time initialisation to finish, confirmed server version 16.1 (`160001`) and UTF-8, copied the files in, and loaded the schema then the data with `psql -v ON_ERROR_STOP=1`. **The SQL loaded with no errors**: 8 tables, 155 rows (roles 3, users 12, audit_logs 78, tickets 24, comments 26, user_claims 0, user_logins 0, user_roles 12).
2. **Verify.** 80 checks, all passed (section 5).
3. **Self-test.** 7 tests, all passed (section 6).
4. **Report.** `MigrationVerificationReport5.html` written. It was checked in a headless browser at desktop and phone widths; a second build from the same JSON is byte-identical.

## 5. Verification results

**VERIFICATION PASSED - 80 of 80 checks; 155 of 155 rows verified identical.**

| Category | Checks | What was checked |
|---|---|---|
| Environment | 3 / 3 | PostgreSQL 16.1 (at least 15), UTF-8, metadata format version 1 |
| Integrity | 2 / 2 | Both SQL files match the SHA-256 recorded at export |
| Counts | 9 / 9 | Each of the 8 tables, plus the total of 155 |
| Hashes | 8 / 8 | The full-content canonical hash of every table matches the one computed on Windows |
| Schema | 34 / 34 | Exactly the 8 expected tables; per table the columns (name, type, length, nullability, default, `GENERATED BY DEFAULT` identity), primary key, foreign keys (names, columns, targets, delete actions) and indexes (uniqueness, `lower(name)` expression, `deleted_at IS NULL` filter); no invalid index |
| Summaries | 10 / 10 | The ten business summaries (users by type and role, active vs soft-deleted, tickets by state and assignment, audit events by action, comments per ticket, totals, date ranges) give the same answers as SQL Server |
| Sanitization | 4 / 4 | Exported sanitized; 12 users; none has a password hash or security stamp and all must reset the password; no two active usernames differ only by case |
| Rules | 10 / 10 | Six identity sequences continue after the loaded ids; `MANAGER` is rejected while `manager` is active; a soft-deleted `manager` can be reused; an orphan comment is rejected; the tests left no rows behind and moved no sequence |

Per-table hashes (first 16 hex characters; identical on both sides): roles `c0a2efd128356144`, users `fa415e1421e2d4a8`, audit_logs `c6e4f24be7acad70`, tickets `c34f64ec58233df7`, comments `c954517fcb3a64cb`, user_claims and user_logins `e3b0c44298fc1c14` (empty), user_roles `44553a2bae5a2d40`.

| Test | Result |
|---|---|

Also confirmed by hand: the container publishes no port; the password is not in the container's environment or `docker inspect`, and the password file is gone from the container after start-up; no Docker volume is left behind by the self-test; no password or credential value appears in the repository or the output.

## 7. Where the built tool differs from the plan, and why

| Plan | Built | Why |
|---|---|---|
| Image `postgres:16` | `postgres:16.1` | Already on this machine (no download), pinned for repeatability, and the version iteration 4's load proof used. The tool still refuses anything older than 15. |
| Password in `POSTGRES_PASSWORD` | Handed over as `POSTGRES_PASSWORD_FILE`, deleted after start-up | An environment variable is stored in the container's configuration and shown by `docker inspect`; a file removed after start-up is not. |
| Read the expected file hashes through the database after the container is up | Read with `grep` from the metadata on the host, before anything starts | The plan's only reason for the database route was "no `jq`"; `grep` for a 64-character hex value is enough, and a corrupted file is now refused before a container exists. |
| A failing hash names the table and the column (via an optional `columnSha256`) | Names the table only | The metadata has no per-column hashes. Adding them is a change to iteration 4's export; the table-level result, together with the counts, schema and summary checks, was judged enough for now. |
| The self-test reloads and damages the delivered database's container | Uses a separate temporary container | So running the self-test can never damage or replace the delivered database. |
| The self-test's negative cases were manual acceptance tests | Automated in `selftest` (tampered hash, corrupted input, existing database, Docker unavailable) | Repeatable on every run. Docker unavailable is simulated with an unreachable `DOCKER_HOST`, so the other containers on the machine are not stopped. |
| Report built "with bash and standard text tools" | Built by `psql` inside the container from the JSON (`report.sql`), in the `postgres` database | Turning JSON into HTML in bash without `jq` is fragile; `psql` in the container is already part of the allowed tooling (decision 7). The migrated data is not read. |
| The canonical boolean cell `CASE WHEN col THEN '1' ELSE '0' END` | `CASE WHEN col THEN '1' WHEN NOT col THEN '0' END` | The plan's form turns NULL into `0` instead of `~`. No boolean column in this schema is nullable, so it did not matter here, but it would for a future schema. |
| Four rule tests | Four rule tests, plus a check that the tests left nothing behind | Guards against the `nextval` problem found in iteration 4. |

## 8. Things noticed

- The data contains some oddities that are faithful to the source and not migration errors: some tickets are submitted before their customer's account was created (ticket 16 on 2026-09-07, customer6 created 2026-09-11), audit ids do not run in time order, and some customers' second comments are timestamped before their first. The verification compares with the source, not with business rules, so these pass; a future sanity check ("created before used") would flag them.
- A container `mar-postgres-iter4` (image `masterantique-postgres:iteration4`, built on `postgres:16.1` with differently named SQL files) is still running on this machine, although `ITERATION4.md` says its throwaway container was removed. It is not used by iteration 5 and was left untouched.
- A bug found after the run and fixed: `verify` run after `report` failed with "Permission denied" on `/tmp/verification-results.json` inside the container, because `report` had copied a file of that name in (owned by the host user) and Linux's `protected_regular` rule stops even root from overwriting another user's file in `/tmp`. `ingest.sh` now deletes the old file before `verify`, and `report` uses its own file names; `verify` → `report` → `verify` was then run twice in a row, all passing. `all` was never affected (it runs `verify` before `report`).
- Line endings: `.gitattributes` pins the files to LF; a fresh clone on Windows and Linux has not been tested yet.

## 9. Known differences and limitations

- The verification is against a record made at export, not the live SQL Server database. It guards against mistakes, not tampering: anyone with write access could change both the record and the SQL.
- Identifiers are lowercase snake_case (a parity note for Phase 2, not a data change); data values are unchanged.
- Timestamps have no time zone, and whether the legacy application stored UTC or local time is unknown; no conversion was made.
- Usernames are unique regardless of case only through the `lower(name)` index; **Phase 2 sign-in must compare `lower(name) = lower(:input)`**.
- Credentials are invalidated: every migrated user must set a new password.
- Decision 16 is settled: [PostgreSQLDatabaseGuide.html](PostgreSQLDatabaseGuide.html) explains how to connect (psql, application logins, network routes, a tested Spring Boot 4.1.1 project with a first-login password change). The container has no published port and no known owner password by design, so applications need a login and a route set up as the guide describes.

## 10. How to repeat it

On a Linux machine with Docker Engine running, from the repository root:

```
tools/phase1/dbmigrate/iteration5/ingest.sh all --recreate
```

Exit codes: 0 success, 1 verification or self-test differences, 2 configuration, tool or Docker error, 3 refused. See `tools/phase1/dbmigrate/iteration5/README.md`.

## 11. Conclusion

The SQL Server database, exported on Windows by iteration 4, was loaded into PostgreSQL 16.1 in a Docker container on Linux by a repeatable script, with no errors. All 155 rows in all 8 tables are identical to the source (every table's full-content hash matches), the schema is as designed, the ten business summaries agree, no credentials were carried over, and the database rules behave as in the legacy system. The tooling proved it catches damage, tampering and corrupted input. Iteration 5 meets its plan.
