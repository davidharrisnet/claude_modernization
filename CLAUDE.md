## What this repo is

A two-phase legacy-to-modern migration exercise (see [README.md](README.md)) simulating a common engagement pattern: modernizing legacy .NET applications to Java/Angular for federal customers. The goal is not production-grade code — it's demonstrating *how* an AI-assisted migration is reasoned through, including what would be flagged as risk. This repo is where Claude Code is used to plan and drive the Phase 2 modernization.

### The database migration (model layer)
Two tools for PostgreSQL: `export-postgresql` = SQL Server → sanitized PostgreSQL files (Windows, export only); `import-postgresql` = those files loaded into PostgreSQL in Docker on Linux and verified against the export metadata. Two more for an Oracle proof of concept (added 2026-09-24): `export-oracle` and `import-oracle` (both built and run 2026-09-24). Earlier SQLite and MySQL experiments were removed from the working tree (they remain in git history and the `model-iteration*` branches). See [docs/phase1/dbmigrate/DATA_MIGRATION.md](docs/phase1/dbmigrate/DATA_MIGRATION.md) for the overall strategy (pipeline, decisions, security policy) and `docs/phase1/dbmigrate/<tool>/` for each tool's description and reports. Phase 2's database is **PostgreSQL, not Oracle** (user decision, 2026-09-23), despite the README brief naming Oracle: the PostgreSQL pair is the migration to the final target. The Oracle pair (user decision, 2026-09-24) is an additional proof of concept that shows the same migration reasoned through for the Oracle the brief names; it does not change the Phase 2 database.

**Execution environments differ by tool and this matters for what Claude Code can actually run:**
- **export-postgresql** runs on a Windows machine with Visual Studio 2017, ASP.NET Framework 4.7.2, and SQL Server all preinstalled. Its export step needs a live SQL Server LocalDB connection and PowerShell — neither exists elsewhere, so it cannot be executed from a Linux session at all; changes to its tooling can be authored anywhere but must be run on that Windows machine.
- **export-oracle** has the same environment as export-postgresql (Windows, LocalDB, PowerShell 5.1) and is export only, so its SQL is proven only when import-oracle loads it into Oracle on Linux.
- **import-postgresql** (and import-oracle) run on a Linux machine with none of the Microsoft tooling installed. It cannot connect to SQL Server, so it starts from the three files already exported and sanitized on the Windows side (sanitization happens inside the export, in memory, before anything is written — see `docs/phase1/dbmigrate/DATA_MIGRATION.md` §2/§5.2) — it is genuinely runnable end-to-end (load/verify/selftest/report) in a Linux Claude Code session.

### Phase 1 — Legacy Build (complete, in sibling repo)
- Stack: ASP.NET Framework 4.7.2, C#, MVC or WebForms, SQL Server (or SQLite)
- A small domain with 3–4 related entities (e.g., Requests → Assignees → Status History), CRUD, a 3+ state approval/status workflow, hardcoded-role login, and a filtered/paginated list view
- Required: layered architecture (UI / business logic / data access separated — no logic in code-behind), server-side validation, logging of workflow state changes (this becomes the Phase 2 audit trail), and a README explaining structure and how to run it

### Phase 2 — AI-Assisted Modernization (in progress: DB migration done (export-postgresql and import-postgresql); model layer of the Spring Boot backend started; controller, security and Angular view not started)
- Stack: Angular 21, Spring Boot, **PostgreSQL, not Oracle** (user decision, 2026-09-23); the README brief says Oracle. The README says Spring Boot 3 in one place and Java 21 / Spring Boot 4.0 in another; the user chose **Spring Boot 4.1.1 on Java 21** for the backend (2026-09-23). The backend runs on the migrated PostgreSQL database.
- Feature parity with Phase 1 (same entities, workflow, auth boundary); any parity gaps must be noted and explained
- A REST API in Spring Boot backing the Angular SPA (no server-rendered views)
- A data migration plan/script from the SQL Server schema to the target database, noting type/logic differences (the brief says Oracle; done for PostgreSQL by export-postgresql and import-postgresql, see `docs/phase1/dbmigrate/DATA_MIGRATION.md` §8)
- Required: server-side validation and injection/XSS protections, no secrets in source, one unit test suite per layer (Spring service layer, Angular component), clear separation of concerns (no logic in controllers/components), WCAG 2.1 AA basics on the Angular UI, a migration notes doc, and preserved/improved workflow audit logging

### Deliverables
1. Working legacy app (Phase 1 scope)
2. Working modernized app (Phase 2 scope), with parity gaps explained
3. A 1–2 page migration notes doc: key decisions, risks to flag in a real migration, what would be done differently with more time
4. A brief walkthrough of how Claude was used — what it did, and what was double-checked or overridden
