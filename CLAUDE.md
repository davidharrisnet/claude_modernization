## What this repo is

A two-phase legacy-to-modern migration exercise (see [README.md](README.md)) simulating a common engagement pattern: modernizing legacy .NET applications to Java/Angular for federal customers. The goal is not production-grade code — it's demonstrating *how* an AI-assisted migration is reasoned through, including what would be flagged as risk. This repo is where Claude Code is used to plan and drive the Phase 2 modernization.

### Migration iterations done so far (database layer)
Iteration 1 = SQL Server → SQLite on Windows; iteration 2 = SQLite in a Dockerized Linux container; iteration 3 = SQLite baked into a custom Docker image, independently verified and credential-sanitized, run entirely on Linux; iteration 4 = SQL Server → sanitized PostgreSQL files (Windows, export only); iteration 5 = those files loaded into PostgreSQL in Docker on Linux and verified against the export metadata; plus a MySQL-in-Docker extra. See [docs/phase1/dbmigrate/DATA_MIGRATION.md](docs/phase1/dbmigrate/DATA_MIGRATION.md) for the overall strategy (pipeline, roadmap, security policy) and `docs/phase1/dbmigrate/iteration{N}/` for each iteration's plan/record/reports. Phase 2's database is **PostgreSQL, not Oracle** (user decision, 2026-09-23), despite the README brief naming Oracle: iterations 4–5 are the migration to the final target, and no Oracle dialect will be built.

**Execution environments differ by iteration and this matters for what Claude Code can actually run:**
- **Iterations 1 and 2** run on a Windows machine with Visual Studio 2017, ASP.NET Framework 4.7.2, and SQL Server all preinstalled. Their export step needs a live SQL Server LocalDB connection and PowerShell — neither exists elsewhere, so these iterations cannot be executed from a Linux session at all; changes to their tooling can be authored anywhere but must be run on that Windows machine.
- **Iteration 3** runs on a Linux machine with none of the Microsoft tooling installed. It cannot connect to SQL Server, so it starts from `01-schema.sql` + the sanitized data file already exported and sanitized on the Windows side (sanitization happens immediately after export, on the Windows machine, before anything is copied elsewhere — see `docs/phase1/dbmigrate/DATA_MIGRATION.md` §2/§5.2) — it is genuinely runnable end-to-end (build/verify/selftest) in a Linux Claude Code session.

### Phase 1 — Legacy Build (complete, in sibling repo)
- Stack: ASP.NET Framework 4.7.2, C#, MVC or WebForms, SQL Server (or SQLite)
- A small domain with 3–4 related entities (e.g., Requests → Assignees → Status History), CRUD, a 3+ state approval/status workflow, hardcoded-role login, and a filtered/paginated list view
- Required: layered architecture (UI / business logic / data access separated — no logic in code-behind), server-side validation, logging of workflow state changes (this becomes the Phase 2 audit trail), and a README explaining structure and how to run it

### Phase 2 — AI-Assisted Modernization (in progress: DB migration done through iteration 5; model layer of the Spring Boot backend started; controller, security and Angular view not started)
- Stack: Angular 21, Spring Boot, **PostgreSQL, not Oracle** (user decision, 2026-09-23); the README brief says Oracle. The README says Spring Boot 3 in one place and Java 21 / Spring Boot 4.0 in another; the user chose **Spring Boot 4.1.1 on Java 21** for the backend (2026-09-23). The backend runs on the migrated PostgreSQL database.
- Feature parity with Phase 1 (same entities, workflow, auth boundary); any parity gaps must be noted and explained
- A REST API in Spring Boot backing the Angular SPA (no server-rendered views)
- A data migration plan/script from the SQL Server schema to the target database, noting type/logic differences (the brief says Oracle; done for PostgreSQL in iterations 4–5, see `docs/phase1/dbmigrate/DATA_MIGRATION.md` §8)
- Required: server-side validation and injection/XSS protections, no secrets in source, one unit test suite per layer (Spring service layer, Angular component), clear separation of concerns (no logic in controllers/components), WCAG 2.1 AA basics on the Angular UI, a migration notes doc, and preserved/improved workflow audit logging

### Deliverables
1. Working legacy app (Phase 1 scope)
2. Working modernized app (Phase 2 scope), with parity gaps explained
3. A 1–2 page migration notes doc: key decisions, risks to flag in a real migration, what would be done differently with more time
4. A brief walkthrough of how Claude was used — what it did, and what was double-checked or overridden
